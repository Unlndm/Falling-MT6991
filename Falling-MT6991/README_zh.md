# Falling-MT6991

天玑 9400（MT6991）调度模块，Magisk / KernelSU / APatch 都能刷。

- 适用：MT6991 · Android 15/16 · 内核 6.6+
- 版本：v3.6.1
- 实测机型：一加 Ace 5 至尊版（PLC110），KernelSU，SELinux Enforcing
- 作者：弦起悲歌赴寒江

## 功能

| 功能 | 说明 | 位置 |
| --- | --- | --- |
| 智能调度 | 按温度 / 整机与分簇占用率 / 帧率 / 前台应用 / 屏态自动选档，不用手动设置 | `lib/smart.sh` |
| 决策遥测 | 每次换档记一行（原因/分数/温度/占用/帧率），并累计各档驻留时长 | `config/runtime/smart.trace`、`smart.stats` |
| 存活监控 | 守护异常退出自动退避重启；死循环崩溃不会静默失效 | `service.sh` |
| 游戏调度 | 官方 / 模块二选一：交官方让路，或模块接管保底中度游戏档 | `config/system.conf` 的 `game_mode` |
| 频率档位 | 三簇调速器 / 频率上下限 / 速率限制 / GPU / cm_mgr（内部资源，由智能调度调用） | `config/profiles/` |
| 调度策略 | PELT 响应 / MTK uclamp / 触控 boost / hmbird 参数（随档位自动切换） | `config/profiles/sched_*.conf` |
| 智能温控 | 恒开：<55℃ 全速 · 55-70℃ 85% · 70-80℃ 70% · >80℃ 55%，温度回落还原档位上限 | `lib/thermal.sh` |
| 触控采样率 | 日常 / 游戏两档，也能给单个应用指定 | `config/触控.md` |
| 应用策略 | 按包名指定档位，优先于自动评分 | `config/apps.conf` |
| 极致省电 | 叠加在当前档位之上的全局限制层（非新档位）：压 CPU/GPU 上限、锁升频节奏、关 boost/cm，任意档位下生效；游戏期间自动失效 | `config/system.conf` 的 `extreme` · `config/profiles/extreme_overlay.conf` |
| ZRAM | 按 12/16/24G 改写 oplus_mm_config.xml，开机 bind 覆盖 | `odm/etc/` |

## 游戏怎么处理

先回答「哪些是游戏」：你在 WebUI「触控 → 游戏包名」里填，逗号分隔，填了才算。
再回答「游戏交给谁」：调度页 → 游戏调度，二选一。

| 模式 | 模块动作 | 适合 |
| --- | --- | --- |
| 官方调度（默认） | 整体让路：不写调速器、不写频率、不做智能选档，只切游戏采样率；进入让路时把调度层节点还原成出厂，避免和官方风驰叠加 | 官方 HyperBoost / 风驰已经能压住帧率 |
| 模块调度 | 接管：`game_medium` 保底（2.2 / 2.7 / 3.1 GHz，升频快、上限低于性能档），帧率 <60% 或 CPU 占用 ≥85% 才升 `performance` | 官方调度保守、帧率不稳 |

两种模式共用同一套安全线：温度 ≥54°C 取消保底、≥58°C 强制降档，内核温控照常按比例压频率上限。
不管选哪种，只要检测到官方已经把 governor 切成 `scx`，模块都不会去写 governor。

游戏判定有迟滞：进入立刻生效，退出要连续 15s 没命中（前台没它、进程也没了）才算结束，
避免切后台回个消息就来回换档。被判定为游戏期间，`apps.conf` 里给同一个包写的档位不生效
（游戏优先按上面的模式走），触控采样率照常。

## 极致省电

开启位置：WebUI「我的」页 → 极致省电。它不是一个新的档位，是**叠加在当前档位之上的
限制层**——档位决定基线（性能/均衡/省电/游戏），极致省电把基线整体往下压。

开启后做的事（代价是响应会变慢，这是「极致」的应有代价）：

- CPU 三簇频率上限压到实机频率表的低频点
- GPU 上限压到最低可用频点，关 GPU boost，调速器切 powersave
- 关 cm_mgr 性能模式，开 c2ps 省电模式
- sugov_ext 升频间隔拉大（升得极慢）、降频间隔拉到最小（掉得极快）
- hmbird boost 阈值拉高（很少触发 boost）
- 调度策略一律用最省电的那套

**游戏期间自动失效**：命中游戏名单或游戏进程存活时，限制层整体不生效
（产品硬规则：游戏 CPU 一律不管，游戏不做极致省电）。

参数标定入口在 `config/profiles/extreme_overlay.conf`：实机标定完只改这一个文件，
不动代码。关闭后所有节点还原成出厂值，不会残留省电状态。

## 运行开销

守护进程 5 秒一轮（息屏 15 秒）。v3.0 起**每轮 0 个子进程**，切档时一次性 8 次。

| 项 | 做法 |
| --- | --- |
| 信号采集 | `lib/metrics.sh` 一次收温度 / 整机忙时 / 分簇忙时 / 帧率，全内建 `read` |
| 温度 | zone 路径缓存 60 秒（旧版每个 zone 两次 `cat`） |
| 降频基线 | 读进内存做字符串索引，不再每 policy `grep`+`cut` |
| 可用频率 | `read` 整行 + 词分割取 ≤ 目标的最大值，不再 `cat`+`tr`+`awk` |
| 触控配置 | 内建读全文比对（旧版每轮 `md5sum`+`cut`） |
| 开关 / 应用策略 | `cfg_get` / 内建扫表，不走 `grep` |
| 状态写入 | 内容变了才写，让路期间不再每 5 秒重写同一份控制快照 |
| 运行时目录 | 目录已存在就不 `mkdir`（这个函数每次决策调 3~4 次） |

**切档链路**（换档时才有，5 秒一轮的主循环不受影响）：

| 项 | 旧版 | v3.0 |
| --- | --- | --- |
| 档位解析 `load_profile` | 每行 `printf`+`tr`+`sed` | 参数扩展，零子进程 |
| 取第 i 项 `field` | 每次 `awk` | 内建分词 |
| `write_file` 读写 | 每次两个 `$(cat)` | 内建 `read` |
| `policy_list` | 每次 `ls` | 进程内缓存 |
| `device.conf` 查表 | 每簇两次 `grep`+`cut` | 一次读入内存索引 |
| cpufreq 解锁 | 每次 18 次 `chown`/`chmod` | 先探 1 个节点，已解锁就整段跳过 |
| 日志轮转 | 每条日志一次 `stat` | 每 50 条一次 |
| 逐节点写入日志 | info 级（进 logcat） | debug 级 |

实测（假 sysfs + 同一份档位配置，用命令替换包装计数）：
一次 `apply_profile` 从原先上百次子进程降到 **8 次（首次）/ 7 次（重申）**。

| 页面 | 内容 |
| --- | --- |
| 概览 | Hero 卡片（当前档位 + 温度 + 占用 + 频率）· **帧率闭环仪表** · 调度倾向卡片 · **分簇热力** · CPU/GPU 实时仪表 · 近期事件 |
| 调度 | 当前决策明细 · 游戏调度归属 · 决策规则 · **决策链时间轴** · 档位驻留 · 调度层节点与参数 · 运行状态 |
| 触控 | 触控采样率开关与档位 · 游戏包名 · 专属采样率 · 应用策略 · 应用库 |
| 我的 | 主题与液态玻璃 · 通知与诊断 · 配置管理 · ZRAM · 日志 · 设备信息 |

### 三个原创可视化

调度模块有 NovaSched 没有对等物的东西，所以这三个是自己设计的：

- **帧率闭环仪表**：压力环（追帧压力，颜色冷→暖→热）+ 四段条（帧率达标率 / 大核占用 / CPU 争用 / 温控降额）+ 执行器档位刻度（L0~L4）。
- **分簇热力**：小核/中核/大核三条并列条形。整机占用看不出瓶颈在哪——「小核吃满、大核空转」和「三簇各半」是两回事。
- **决策链时间轴**：把换档记录解析成因果链（方向 + 原因 + 当时的信号标签），而不是一行行原始日志。

### 外观

- **设计体系**：所有颜色/间距/圆角/时长/缓动都是 token（`webroot/theme.css`），组件不写死值；深色模式只覆盖 token。
- **液态玻璃**：WebGL 镜面折射引擎（移植自 NovaSched-Zen-Edition 的 `assets/liquid-glass.js`，Apache-2.0）。一块 WebGL stage 渲染全部玻璃面，每块玻璃在自己元素里放一张画布，折射 + 光谱色散 + 边缘高光全在 fragment shader 里算；纹理有 24MB 上限，静止时零重绘。玻璃材质按角色分级（内容卡 / 面板 / 强调 / dock 指示器 / 小胶囊 / 底栏 / 设置组）。设置页可关（关掉后彻底不跑 WebGL，退回半透明）。
- **应用策略**：规则行是玻璃卡，带应用名与彩色头像；左滑露出删除，点行进弹窗编辑（包名 + 档位 chips），新建时可直接从应用库选包，不必手打。搜索同时匹配包名与应用名。
- 页面切换有双向滑动转场，每页保留自己的滚动位置；跟随系统「减少动效」偏好。

## 使用

- 配置备份：WebUI → 我的 → 配置管理，导出到 `/sdcard/Download/falling_config_backup.tar.gz`
- 日志：`/data/local/tmp/falling_mt6991.log`
- 守护开销：前台应用与亮灭屏改用系统事件流（`logcat -b events` 的
  `wm_set_resumed_activity` / `screen_toggled`）驱动，不再每轮跑 `dumpsys`。
  实测一轮 5s 的阻塞从约 0.95s 降到接近 0；事件流不可用时自动回退 `dumpsys`。
- 卸载：自动停守护、把调度策略/触控采样率/CPU/GPU/cm_mgr 还原到**出厂还原档**（`stock.conf`，不是日常用的均衡档）、解除模块写过的频率上限、还原 cpufreq 权限与温控、卸掉 ZRAM 覆盖、删日志备份，零残留
- 自检：装了模块之后想确认行为对不对，跑 `sh tools/run_device_selftest.sh`——
  它把测试套件推到手机上，用**手机自己的 shell** 跑一遍。
  这一步不能省：Android 的 `/system/bin/sh` 是 mksh，和 bash 有一处要命的差异
  （`${v%%|*}` 的 `|` 被当成模式备选分隔符），本地 bash 全绿不代表真机全绿。
- 只想看本机有哪些可调节点：`adb shell "su -c 'sh /data/adb/modules/falling-mt6991/../tools/probe_device.sh'"`，
  或用仓库里的 `tools/probe_device.sh`（只读，不改任何节点）

## 配置文件

- `config/profiles/<name>.conf`：频率档位（内部资源，由智能调度调用；INI，数组按 policy 顺序，空 = 保持默认）
- `config/sched_profile` + `config/profiles/sched_*.conf`：调度策略（随档位自动切换，不用手选）
- `config/apps.conf`：`SCREEN_OFF_PROFILE=` + `包名=档位` + `包名@touch=采样率码`
- `config/触控.md`：`日常=` / `游戏=` / `游戏包名=`
- `config/system.conf`：功能开关（daemon / touch / game_mode / tendency / notify / debug / zram / theme），`theme` 取 `light` 或 `dark`，`game_mode` 取 `official` 或 `module`，`tendency` 取 `save` / `balance` / `perf`
- `config/runtime/`：运行时状态，备份与卸载自动清理

### 调度倾向（省电 / 均衡 / 性能）

WebUI → 智能调度 → 「调度倾向」分段控件。**它不锁档位**，只是给自动决策加一个固定偏置：

| 倾向 | 偏置 | 效果 |
| --- | --- | --- |
| 省电 `save` | −15 | 更容易落到省电档，更难升到性能档（默认） |
| 均衡 `balance` | 0 | 不偏不倚，按现场信号自动判断 |
| 性能 `perf` | +15 | 更容易升到性能档，更难掉到省电档 |

v3.5.0 起默认是**省电**倾向，并把「均衡档」重标定成真正的**日常省电档**：
CPU 三簇上限从接近满频（2.4 / 3.3 / 3.6 GHz）降到各簇最高频的约 75%
（1.8 / 2.4 / 2.8 GHz），GPU 上限从 1508 MHz 降到 988 MHz，`cm_mgr`
性能模式关闭，闭环执行器封顶 L2。
这些取值都来自实机频率表（`docs/arch-realdevice.md`），不是估计值。
需要更高性能时智能调度仍会升到 `performance`（2.4 / 3.3 / 3.73 GHz）。

硬规则**不受倾向影响**——下面这四条在评分之前就已经返回了，倾向碰不到它们：

- 息屏 → 极限省电
- 温度 ≥58°C → 强制降档
- `apps.conf` 里给某个 App 显式指定的档位
- 游戏保底（`game_mode=module` 时的 `game_medium`）

偏置只加在「综合评分」这一步，所以它改变的是「多容易升档 / 多容易掉档」，
不是「升到哪一档」。写 `config/system.conf` 的 `tendency` 键，守护 20 秒内生效。

### 三层控制链（档位是怎么真正落到硬件上的）

这是 v3.1 改完后的结构。**之前是三处抢同一批节点、互相覆盖**，
现在是每个节点只有一个写入者。

| 层 | 文件 | 干什么 | 写哪些节点 |
| --- | --- | --- | --- |
| 决策层 | `lib/smart.sh` | 每 5 秒打分，决定用哪个档位 | 不写节点 |
| 执行层 | `lib/loop.sh` | 帧率闭环 + 上限决策 | `scaling_max_freq`、`sugov_ext` 速率、`hmbird` 阈值 |
| 调度层 | `lib/sched.sh` | 按档位写调度策略 | PELT / uclamp / isolate / misfit（不含 `cpuctrl_*`） |
| 温控层 | `lib/thermal.sh` | 只出降额比例 | 不写节点（比例交给执行层落盘） |
| 频率层 | `lib/governor.sh` | 调速器与最低频率 | `scaling_governor`、`scaling_min_freq` |

**为什么档位重心不放在 `scaling_max_freq` 上**：实机测过，这台机器上
ColorOS 自己在高频改这个节点（p0 在 1200M↔2400M 之间跳），写上去几秒就被改回去。
真正稳的是 `hmbird` 百分比阈值（60 秒纹丝不动）和 `sugov_ext` 升降频速率
（能撑 50 秒，但需要每轮重申）。完整实验数据见 `docs/arch-realdevice.md`。

**帧率闭环**：用帧率达标率（EMA 平滑）+ 大核占用 + 温度算「追帧压力」，
映射到执行器档位 L0~L4。帧率富余就收紧（省电），帧率不足就放开（追帧）。
带滞回：连续 2 轮结论一致才换档，且两次换档至少隔 20 秒。
频率上限只在追帧压力 ≥60 时才抬回目标——平时让位给系统，不抢同一个节点。

**让路是干净的**：切到「官方调度」时，模块会把自己之前写进节点的频率上限
恢复到出厂值（`cpuinfo_max_freq`），并把调度层还原出厂。
只是「不再写」等于让了一半，留在节点上的上限会压住官方风驰。

### 智能调度怎么算的

`lib/smart.sh` 每 5 秒给当前状态打一次分，分数决定档位（越高越偏性能）：

| 项 | 取值 |
| --- | --- |
| 基础分 | 40 |
| 温度 | ≥60°C −40 · ≥55°C −25 · ≥50°C −12 · <42°C +6 |
| 整机占用率（5 秒窗口） | ≥85% +25 · ≥55% +10 · ≤12% −18 |
| 大核占用率 | ≥90% +18 · ≥70% +10 · ≥50% +4（只有加分，不扣分） |
| 帧率 | 低于 60% +30 · 连续 2 轮低于 80% +20 · 连续 6 轮 ≥97% −12 |
| CPU 争用（PSI） | `some avg10` ≥20% 且整机或大核占用 ≥45% 时 +12（二级判据，缺失节点则跳过） |
| 调度倾向 | 省电 −15 · 均衡 0 · 性能 +15（只在这一步加，硬规则不受影响） |

占用率用 `/proc/stat` 两次采样算，不是 `loadavg`：`loadavg` 是 1 分钟指数衰减，
开游戏后二三十秒才爬上来，5 秒轮询几乎看不出变化；双采样说的是「这 5 秒 CPU 到底在干什么」。
信号全部由 `lib/metrics.sh` 一次采集：整机忙时读首行，分簇忙时读 `cpuN` 行、
按 `policy*/affected_cpus` 归并成小核 / 中核 / 大核三档（映射缓存，不每轮重扫）。

**为什么要看分簇**：整机 45% 可能是「小核全满、大核全闲」（瓶颈在并行度/迁移，
提频收益很小），也可能是三簇各 45%（真的需要频率）。只看整机会把前者误判成后者，
结果就是频繁升档却没效果。所以大核吃满才额外加权。
只做正向加分不做负向扣分——小核忙不代表不需要性能，扣分就是直接把卡顿做出来。

**为什么要看 CPU 争用**：`/proc/stat` 算的是「平均利用率」，会把「任务在排队等 CPU」
平均掉——利用率没到顶，但任务在等（突发负载、多任务争用）时，平均利用率看不出来。
PSI 的 `some avg10` 直接量化这段等待时间。它只当二级判据：CPU PSI 只说明供给不足，
10 秒平滑还会吞掉短卡顿，所以必须叠加一个绝对需求下限（整机或大核占用 ≥45%）才加分——
轻载下几个后台线程在小核排队就能把 PSI 顶到两位数，单用 PSI 会把频率白抬起来。
权重是 +12 而不是更高：实机轨迹显示轻载基线分约 19，回到均衡的门槛是 39，
+20 会让 PSI 这一个噪声信号单独跨过门槛，造成省电档与均衡档每 20 秒来回跳
（`smart.trace` 实测 10 分钟 13 次换档）；+12 时不会跨门槛，真实负载仍靠
整机占用、大核占用、低帧三项叠加升档。
本机没有 `/proc/pressure/cpu`（内核未开 `CONFIG_PSI`）时返回 −1，该信号整体跳过。

分数 ≥62 升性能档、≤23 降省电档，中间是均衡档。防抖：一次只跳一档；升档要越过 62、
降档要跌破 54（省电侧 23/39），非温度原因的换档至少间隔 20 秒。
温度 ≥58°C 直接强制降档、不看防抖；`apps.conf` 里显式指定的档位在温度 <54°C 时优先。
应用策略里的档位名如果不存在（拼错 / 档位文件被删），会被直接忽略并记一条错误日志，
不会拿坏名字去写，也不会每 5 秒重试刷日志（应用失败统一退避 30 秒）。
每一步都写 `config/runtime/smart.state`，调度页就是读这个文件显示原因。

**决策历史**：每次换档往 `config/runtime/smart.trace` 追加一行
`时间 原档>新档 原因 分数 温度 整机占用 大核占用 帧率 争用`，环形保留 240 条；
`smart.stats` 累计各档位驻留秒数。这两份是「为什么又降档了」的第一手依据，
调度页直接展示，不用翻 logcat。

### 调度策略怎么写

`sched_*.conf` 里的键名必须能在 `lib/sched.sh` 的节点表里找到，写错不会报错、只会静默跳过
（v1.2.0 之前 `sched_daily.conf` 就有 8 个键名对不上，实际一直没生效）。改完跑一次自检：

```sh
sh /data/adb/modules/falling-mt6991/lib/sched.sh check
# 每档一行: 未知键 / 值越界 / 本机缺节点；最后 OK 或 FAIL
```

自检会拒绝三类写法：键名不在节点表、值超出内核可接受范围（如 `PELT_MULTIPLIER` 只认 1/2/4）、
节点在本机内核不存在（这一类只统计，不算错，属于探测式跳过的正常情况）。
被拒的项会记到 `config/runtime/sched.badkeys`，WebUI 调度页「调度层节点」也能看到。

写档位时只还原「上一档写过、这一档不再需要」的键，不会先全量恢复出厂再写一遍；
同一档被重复调用（守护进程每 300s 的抗重置重申）只补被系统改回去的值，不重写全部，
计数写在 `config/runtime/sched.drift`。


## 出问题先看这几条

1. root 管理器授权了吗（KernelSU 要在 App 里允许）
2. 频率没变：看 WebUI CPU 子页的实时频率；厂商回锁属于平台行为，改不了
3. 触控没切：确认 `触控.md` 的命令跟机型节点对得上（一加 Ace5 系列是 `182`）
4. 主题不生效：确认 `system.conf` 里有 `theme=` 键（WebUI 会自动补写，值只能是 `light` / `dark`）
5. 开不了机：Recovery 里删掉 `/data/adb/modules/falling-mt6991`
6. 频率上不去：先看 WebUI 调度页「分簇占用」。大核没吃满时模块不会升性能档，
   这是设计（整机满载 ≠ 需要提频）。若确实需要，把 `config/system.conf` 的
   `tendency` 改成 `perf`
7. 游戏时没跑官方风驰：确认 `game_mode=official` 且该包名登记在 `触控.md` 的游戏名单里。
   模块让路时会先撤掉自己的频率上限，不会压住官方调度
