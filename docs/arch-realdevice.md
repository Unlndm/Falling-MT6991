# 实机架构实验记录 — v3.1 调度重写的依据

设备：**一加 Ace 5 至尊版 / PLC110 / MT6991 / Android 17 (SDK 37) / 内核 6.6.118 / KernelSU**
ROM：ColorOS。拓扑：policy0 = CPU0-3（小）、policy4 = CPU4-6（中）、policy7 = CPU7（大）。

本文档记录 v3.1 调度架构重写的**全部依据**。所有数字都来自本机受控实验，
不是来自通用模型、不是猜的。原始探测脚本在 `tools/probe_*.sh`。

---

## 一、核心问题：为什么原来那套「写死频率上限」不管用

原架构把档位差异主要体现在 `scaling_max_freq` 上（性能档写 3730000，省电档写 2200000）。
实机观察发现：**这个节点是系统自己在高频抢占**。

### 实验 1：scaling_max_freq 是否被系统改

30 秒内每 3 秒采一次：

```
t=1  p0=1200000  p4=1800000  p7=1400000
t=4  p0=2400000  p4=2600000  p7=3600000   <- 被抬上去
t=7  p0=1200000  p4=1800000  p7=1400000   <- 又被压回来
...
```

**p0 在 1200000↔2400000 之间反复跳，p7 在 1400000↔3600000 之间反复跳。**

已排除其他模块干预：AppOpt、CZero、TA_utl、violet_box_module 全都不碰 cpufreq。
结论：是 ColorOS 自身的调度策略在管这个节点。

**推论**：模块写上去的省电上限，几秒内就被系统改回；模块写上去的性能上限，
也可能被系统随时压下来。**「档位 = 一个绝对频率」这个模型在这台机上不成立。**

## 二、三类执行器的「存活能力」实测

这是 v3.1 架构重排的直接依据。三个候选写入点，各做了一次持续性实验。

### 2.1 `sugov_ext/*_rate_limit_us` —— 半可靠，但效果极强

节点：`/sys/devices/system/cpu/cpufreq/policyX/sugov_ext/{up,down}_rate_limit_us`

**实验 2：写不同值，看 CPU 实际能跑到哪**

```
写入 up=200000  ->  CPU 被钉在 798000（地板），完全上不去
写入 up=10       ->  能冲到 3600000（顶）
```

这是**非常强的杠杆**——单个参数就能把大核钉死或放开。

**实验 3：写进去的值能活多久**

```
t=0    写入 up_rate_limit_us = 88888
t=5    88888
t=10   88888
t=15   88888
t=20   10        <- 被系统重置回默认值
t=25   10
```

**能撑约 50 秒不被改，但系统会间歇重置回 10。**
→ 结论：需要守护进程**每轮重申**（每 5 秒）。这是「半可靠」。

（`up_rate_limit_us` = 两次升频之间的最小间隔，单位微秒。值越小 = 升得越快。
所以 200000us ≈ 5.5 秒才允许升一档 = 钉在地板；10us = 几乎不限速。）

### 2.2 `/proc/hmbird_sched/*` —— 最可靠

**实验 4：写进去 60 秒观察**

```
t=0    写入 cpuctrl_high=41, cpuctrl_low=43
t=15   41 / 43
t=30   41 / 43
t=45   41 / 43
t=60   41 / 43      <- 纹丝不动
```

**60 秒内完全没被系统碰过。**

而且这些是**百分比语义**（boost 触发/退出的 util 阈值），不像绝对频率那样
天然会被系统的动态策略覆盖。→ 这层应该是档位的主力。

### 2.3 `scaling_max_freq` —— 不可靠，但仍是必要的兜底

见实验 1。系统高频抢占。

但它不能完全废弃：追帧时需要**一个硬上限以外的兜底**，而且温控降额
（防过热）需要一个落点。所以保留，但**降级为兜底**，且只在追帧压力高时抬。

## 三、可靠度分级 → 架构重排

| 执行点 | 可靠度 | 证据 | v3.1 归属 |
|---|---|---|---|
| `hmbird_sched/*` | **最可靠** | 60s 纹丝不动 | 档位主力（cpuctrl_high/low） |
| `sugov_ext/*_rate_limit_us` | 半可靠 | 撑 50s，需重申 | 档位主力（升降频节奏） |
| `scaling_max_freq` | 不可靠 | 系统高频抢占 | **降级为兜底**，仅追帧时抬 |

### 新增的执行器档位表（实测调出来的）

```
level 0..4 → up_rate(us):   3000 1500  700  300   10
           → down_rate(us):   10   10  100 1000 10000
           → cpuctrl_high:    80   70   60   52   45
           → cpuctrl_low:     60   52   45   40   35
```

语义：level 越大 = 升频越快 + boost 阈值越低 = 越激进。
省电档（L0）升频慢（3000us 一档）、降频快（10us）→ 典型的省电曲线。
性能档（L4）升频几乎不限速（10us）、降频很慢（10000us）→ 追帧不丢。

## 四、控制链重构：一个节点只能有一个写入者

**改之前的乱象**（三处抢同一批节点，互相覆盖）：

```
governor.sh  →  scaling_max_freq + sugov_ext 速率
thermal.sh   →  scaling_max_freq（温控自己降频）
sched.sh     →  hmbird cpuctrl_high/low
```

后果举例：温控把上限压到 2.1G → governor 下一轮按档位又写回 3.3G →
再下一轮温控再压……来回抖。

**v3.1 之后**：

```
scaling_max_freq   → 只归 cap_apply()      (lib/loop.sh)
sugov_ext 速率     → 只归 loop_apply_exec() (lib/loop.sh)
hmbird cpuctrl_*   → 只归 loop_apply_exec() (lib/loop.sh)
governor.sh        → 只写调速器 + 最低频率，不碰上限
thermal.sh         → 只出降额比例 TH_RATIO，不写任何节点
```

温控的比例通过参数传给闭环层，由闭环层统一落盘 → 永不打架。

## 五、让路：原来只是「半让」

**原实现**：切到「官方调度」时，模块只是「不再写 CPU 参数」。
但模块**之前写进节点的 `scaling_max_freq` 还留在那里** —— 会压住官方风驰。
等于让了一半，让不干净。

**v3.1**：让路时调 `cap_release()`：
1. 各簇 `scaling_max_freq` 恢复到 `cpuinfo_max_freq`（出厂上限）
2. 清掉自己的记录（`cap.base` / `cap.state`）
3. 调度层 `sched.sh reset` 还原出厂
4. 让路期间闭环层完全不跑（`LAY_ROUTE=1` 时跳过 `loop_tick`）
5. 例外：**≥70°C 仍然兜底降额**——安全优先于「不干预」

这个坑是 Kin-Daemon 的 `CODE_WIKI.md` 明确点出来的（它管的是「风驰交接时解除
自己的频率上限」），本模块之前踩了同一个。

## 六、其它实机发现

### 6.1 Android 17，不是 15/16

`ro.build.version.release = 17`，`sdk = 37`。模块原先按 15/16 写的兼容性假设
需要复核。KernelSU（非 Magisk），SELinux Enforcing。

### 6.2 帧率解析必须用 `od` 验证

`/sys/kernel/fpsgo/fstb/fpsgo_status` 的表头里 `targetFPS` 与 `FPS_margin`
之间是**空格不是 tab**，数据行第 5 列常为空。用 `read a b c d e` 会取错列。

`od -c` 验证后确认正确的两列是当前帧率与目标帧率。
配套用 `fstb_tfps_info` 交叉验证（QQ 的 `target_fps:63` 对应行正是 `63 63`）。

### 6.3 温度口径要统一

`thermal.sh` 原来只扫 `cpu-*` / `soc-*` zone，漏了 `gpu*` 和 `soc_max`，
导致 UI 显示的温度与温控实际用的温度不是一回事。已统一。

### 6.4 温度阈值（原 55/58°C）偏保守

实机数据（**已剔除我自己制造的满核进程污染**）：

| 场景 | 温度 |
|---|---|
| 纯待机 | 44~50°C |
| 刷短视频（抖音 89% CPU）+ 充电 | 52~55°C |
| max 口径偶发单 zone 尖峰 | 68.9°C |

55/58°C 在日常高负载下只是刚到边缘，**建议小幅上调即可，不必大改**。
但「所有 zone 取最大值」会有抖动 —— 用 max 口径判定降频要留滞回。

### 6.5 分簇占用实测

刷抖音时（整机 42% / 小核 55% / 大核 10%）：正是「大核吃满才加权」要防的场景，
模块**不会**去升性能档。分簇信号设计意图得到印证。
